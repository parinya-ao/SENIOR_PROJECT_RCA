## Local implementation and wiring limits

The raw campaigns were produced by the strict RCA path in [probes.py](/home/parinya/unversity/lora/experiments/updi_rca/src/updi_rca/probes.py), not by `external/upditerm`. It opens pySerial exclusively with parity even, two stop bits, one-second read/write timeouts and flow control disabled. It sends a one-byte `00` at 300 baud, reads one byte, and labels the transaction `LOCAL_ECHO` unless the byte matches. It sends SIB/LDCS only after both such reads match. Thus the raw record establishes a successful one-byte host API write and a short/empty serial read; it does not show voltage at CP2102 TXD/RXD or at the AVR pin.

The actual vendored Upditerm source is a separate nested repository: origin `https://github.com/streef/upditerm.git`, HEAD `f2222b02ceeff7668caab0f240d2e13298116356` (2024-05-01; VERSION 1.1). Its working tree had a modified `upditerm.py` (227 insertions/97 deletions relative to HEAD). The checked-in nominal `send_break()` still selects 300 baud, sends `00` through the half-duplex echo check, then restores baud. The patch changes error/cleanup handling around that path. The historical/continuation raw logs were generated by RCA `probes.py`; the Upditerm revision does not explain those raw records. Revision details and source snapshots are under [external_path/sources](../evidence/RCA_PHY_01/external_path/sources/source-revisions.txt).

The [Streef Upditerm README at its pinned commit](https://github.com/streef/upditerm/blob/f2222b02ceeff7668caab0f240d2e13298116356/README.md#updi-interface) and [Microchip pymcuprog README at its pinned commit](https://github.com/microchip-pic-avr-tools/pymcuprog/blob/e2fa9a7f0b9cc413367c51b9ccf19d93cdca6c8d/README.md#serial-port-updi-pyupdi) describe a reference connection with common ground, adapter RX directly to UPDI, and adapter TX through 1 kΩ to that shared node; the Upditerm text says target VCC from the cable is optional. These are two software-project reference topologies, not an inspection of this user's cable or board. The actual series element, TX/RX orientation, ground path, VCC source, connector pinout, cable, and any added circuitry remain unknown.

Microchip's current [AVR128DA complete data sheet DS40002183E](https://ww1.microchip.com/downloads/aemDocuments/documents/MCU08/ProductDocuments/DataSheets/AVR128DA28-32-48-64-Data-Sheet-DS40002183.pdf) (Rev. E, 09/2024; ©2024), Section 35.2.3, describes UPDI as a one-wire, asynchronous half-duplex UART. Section 35.3.1.2 says the debugger must send two consecutive BREAK characters to ensure receipt in all cases. Section 35.3.1.2.1 and Table 35-3 express one-wire BREAK timing in terms of the UPDI recovered-bit/prescaler timing; the worst-case recommended duration at the slowest setting is 24.60 ms. Do not equate that UPDI timing basis one-for-one with host UART bit periods. The captured pySerial format is 8E2: an ideal normal zero byte has ten nominal low host-bit periods (start + eight data + even parity), or 33.333 ms at 300 baud, followed by two high stop periods. That nominal low duration exceeds the 24.60 ms worst-case recommended time if generated ideally. The host event log and exact echo do not measure line levels, pulse duration, or adapter waveform at the MCU; only a physical capture can establish those. Retain the measured `TX`/`LOCAL_ECHO` labels; these data neither prove an invalid BREAK nor imply a protocol/software fault. The older DS40002183C PDF snapshot is retained only as historical corroboration; Rev. E is the cited authority.

## Classic CP2102/9 limits and identity uncertainty

The primary source reviewed was Silicon Labs' [classic CP2102/9 data sheet, Rev. 1.8 (January 2017)](https://www.silabs.com/documents/public/data-sheets/CP2102-9.pdf), not CP2102N or CP2102C. Table 4 applies for VDD=3.0–3.6 V and −40 to +85 °C unless stated. For CP2102 UART I/O, it gives TX output-high minimum `VDD−0.1 V` at `IOH=−10 µA` and `VDD−0.7 V` at `IOH=−3 mA`; `VDD−0.8 V` at `IOH=−10 mA` is typical. Output-low maximum is 0.1 V at `IOL=10 µA` and 0.6 V at `IOL=8.5 mA`; 1.0 V at 25 mA is typical. CP2102 UART input limits are VIH≥2.0 V and VIL≤0.8 V. Table 6 specifies CP2102 VDDOUT as 3.0/3.3/3.6 V min/typ/max for 1–100 mA and states a 100 mA maximum regulator supply current. These limits do not measure either adapter's actual VDD, TX load, target VDD, or rail droop.

Table 13 lists default CP2102 descriptors as VID:PID `10C4:EA60` and serial `0001`, and says those ROM strings are configurable. Both observed adapters report that same descriptor tuple; it is consistent with default genuine CP2102 programming but cannot authenticate silicon or distinguish the two units. No chip marking, bill of materials, provenance, or analog output measurement is available. The datasheet PDF was readable through the official browser extraction; direct shell retrieval was denied with HTTP 403, so no local PDF copy is claimed. The concise table extract and fetch result are explicitly labeled and hashed under `external_path/sources/`.

## Host and Linux evidence boundaries

The official [pySerial 3.5 API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html) specifies that timed `read(size)` may return fewer than `size` bytes and `write(data)` returns a byte count. That supports the distinction seen here: the host write was accepted by the serial API, then the local echo read returned zero bytes. It does not locate the missing byte within USB, CP2102 UART, shared wire, target loading, or host buffering.

The Lane B state note records no matching kernel USB/CP210x/disconnect/EPROTO/EILSEQ/error lines in the four-minute baseline interval. This is a weak negative: the raw kernel query output was not preserved, and there was no usbmon trace. Current [Linux USB error-code documentation](https://docs.kernel.org/driver-api/usb/error-codes.html) describes host-visible URB error conditions. Current [Linux usbmon documentation](https://docs.kernel.org/usb/usbmon.html) says traces represent requests from peripheral drivers to host-controller drivers and may differ from bus transactions if an HCD is faulty. The current [Linux-USB Host Side API](https://docs.kernel.org/driver-api/usb/usb.html) notes that host controllers can differ in fault reporting and recovery. The two current pages exposed no kernel release or document revision date; they were fetched 2026-10-26 21:45 UTC and retained with hashes under `external_path/sources/`. usbmon could correlate a future failed serial exchange with USB request completions/errors, but it cannot show the UART voltage or UPDI waveform.
