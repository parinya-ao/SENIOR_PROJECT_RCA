# AVR128DA28 LoRa firmware

Gateway sends DATA; Tracker receives it and returns ACK. The existing SSOT wire
format carries exactly 11 application bytes (`hello world`) and ACK type `0x03`.
The separate ARQ diagnostic protocol retains its own existing framing and values.

The handwritten application implementations are C++17. Existing Arduino entry
points, RadioLib integration, fixed-capacity buffers and caller-owned protocol
state remain in place. Start with the [source map](src/README.md), the
[hardware pin audit](PIN_MAPPING_AUDIT.md), and the
[ACK/NACK protocol and test guide](docs/testing/LORA_ACK_NACK.md). Historical
source ownership evidence is in [Source Ownership V2](docs/refactoring/SOURCE_OWNERSHIP_V2.md).
The current [architecture](docs/architecture/FINAL_ARCHITECTURE.md),
[regression matrix](docs/testing/REGRESSION_MATRIX.md),
[real-radio evidence](docs/testing/REAL_RADIO_EVIDENCE.md), and
[deletion audit](docs/migration/DELETION_AUDIT.md) are separate focused references.

## Build

The verified setup uses PlatformIO Core 6.2.0, the `atmelmegaavr` platform,
Arduino DxCore 1.6.2, and AVR GCC 7.3.0. PlatformIO selects `AVR128DA28`, a 24 MHz
clock, and `gnu++17`. RadioLib 7.1.2 and Time 1.6.1 are declared in
`platformio.ini`. This AVR toolchain lacks the C++ standard-library headers;
firmware uses the available `<stdint.h>` and `<stddef.h>` without adding an STL.

```sh
pio run
pio run -e sender_arq -e receiver_arq
pio project config
```

The default targets are `sender` and `receiver`. Other role targets are
`sender_hello`, `sender_hello_spi`, `sender_hello_5dbm`, `receiver_5dbm`,
`receiver_spi`, `sender_mvp`, `receiver_mvp`, `sender_arq`, `receiver_arq`,
`sender_arq_test`, `receiver_arq_test`, `sender_arq_radio_only`,
`receiver_arq_radio_only`, `sender_reverse_raw`, `receiver_reverse_raw`,
`sender_arq_radio_only_reverse`, and `receiver_arq_radio_only_reverse`.
The existing `debug` and `release` sections are roleless templates; invoking them
as standalone targets fails the role check.

Builds validate generated hardware configuration without rewriting it. They update
only source provenance manifests and the build-directory identity header. Stale
protected configuration stops the build. The portable protocol, command and diagnostic modules compile with
`-Wall -Wextra -Wshadow -Wconversion -Wsign-conversion`, without `-w` or
`-fpermissive`; vendor compiler options remain unchanged.

## Application configuration

Pins, PHY, wire constants and application image bounds retain their existing SSOT.
Edit `config/application.toml` for diagnostic payloads, log/command capacities,
startup delays, raw-test timing and gateway resource policy, then run:

```sh
python tools/config/application_config.py
```

Only `include/application_config.h` is regenerated by this command. Builds reject
stale policy. Host diagnostic commands and validators read the same TOML, so payload
changes reach both firmware and capture checks. Radio-only diagnostics remain
restricted to one physical attempt; result buffers must have power-of-two capacity.
No upload runs automatically. Rebuild after configuration changes.

## Host tests

Use the existing Python environment (`uv sync --locked` if it needs setup), then:

```sh
uv run --no-sync python -m unittest discover -s tests -v
uv run --no-sync python -m unittest discover -s tests -p test_ssot_protocol.py -v
uv run --no-sync python -m unittest discover -s tests -p test_arq.py -v
```

Host checks require GCC/G++ and Clang; some tests also build firmware with
PlatformIO. Run the full suite after builds finish, because its dependency
snapshot must not race PlatformIO lock-file creation/removal. Native protocol
tests compare exact bytes, boundaries, rollover and state transitions; adapter
tests replace physical MCU/radio I/O and do not prove an RF link.

## Preserved boundaries

Generated board C, the vendor UPDI UART C integration, licensed mcurses, and the
boot assembly/compile-time C contract remain in their original language. Python
host tools remain Python. No repository-wide license is declared; existing
third-party notices remain unchanged.

No migration command uploads firmware or changes fuses, EEPROM, boot Flash, pin
maps or PHY settings. Physical startup, SPI/RF behavior, runtime stack/heap usage,
interrupt latency and prolonged hardware operation remain unverified until an
explicitly authorized hardware validation.
